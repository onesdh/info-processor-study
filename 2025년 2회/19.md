# 문제 19

## 문제

다음은 TCP 통신 과정에서 발생할 수 있는 보안 취약점에 대한 설명이다. 이를 이용한 공격 기법으로 옳은 것은?

TCP는 연결을 수립하기 위해 클라이언트가 서버에 SYN 패킷을 보내고 서버는 SYN-ACK 패킷으로 응답한 후 클라이언트가 다시 ACK 패킷을 보내는 3-way-handshake 과정을 거친다.

이때 공격자는 클라이언트 역할로 수많은 SYN 패킷을 서버에 전송한 뒤 마지막 ACK를 고의로 보내지 않아 서버가 연결 대기 상태를 계속 유지하게 만든다.

이로 인해 서버의 연결 대기 큐가 가득 차면서 정상적인 접속 요청을 처리하지 못하게 되어 서비스 거부 상태가 발생한다.

## 1. 문제에서 묻는 것
"SYN만 대량 전송, 마지막 ACK는 보내지 않음, 연결 대기 큐 고갈" → 어떤 공격인지 묻는 문제다.

## 2. 먼저 알아야 할 개념
### (1) TCP 3-way handshake (연결 수립 과정)
```text
 클라이언트                         서버
     │ ① SYN (연결 요청) ───────────▶ │
     │ ◀──────── ② SYN + ACK (수락)  │  (서버: "반쯤 열린 연결(half-open)"을 큐에 저장)
     │ ③ ACK (확인) ────────────────▶ │  (연결 완성 → 큐에서 제거)
```
서버는 ②를 보낸 뒤 ③이 올 때까지 **연결 정보를 대기 큐(Backlog)에 보관**한다.

### (2) SYN Flooding 공격
```text
 공격자 ──SYN──▶ 서버   (출발지 IP는 보통 위조)
 공격자 ──SYN──▶ 서버
 공격자 ──SYN──▶ 서버   ... 수천~수만 번
 서버 ──SYN+ACK──▶ (응답할 곳 없음)   ③ ACK는 오지 않음
 → 대기 큐가 **반쯤 열린 연결로 가득 참** → 정상 사용자의 접속 불가 (서비스 거부)
```
### (3) 대응 방법
| 방법 | 설명 |
|---|---|
| **SYN Cookie** | 큐에 저장하지 않고, SYN+ACK의 시퀀스 번호에 **정보를 인코딩**해 ACK가 오면 검증 |
| 대기 큐 크기 증가 | 임시 완화 |
| 타임아웃 단축 | 오래된 반쯤 열린 연결을 빨리 제거 |
| 방화벽/IPS | SYN 과다 요청 차단 |

### (4) 다른 서비스 거부(DoS) 공격과 구분
| 공격 | 방식 |
|---|---|
| **SYN Flooding** | SYN 대량 + ACK 미전송 (**3-way handshake 악용**) |
| UDP Flooding | UDP 패킷 대량 전송 |
| Smurf | 위조된 ICMP 브로드캐스트로 **증폭** |
| Ping of Death | 비정상적으로 큰 ICMP 패킷 |

## 3. 문제 풀이
| 단서 | SYN Flooding |
|---|---|
| 수많은 SYN 패킷 전송 | ✅ |
| 마지막 ACK를 고의로 안 보냄 | ✅ |
| 서버의 **연결 대기 큐**가 가득 참 | ✅ |
| **서비스 거부** 상태 | ✅ |
