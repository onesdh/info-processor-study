### 패턴 상세 설명 (23개 전체)
> 각 패턴을 **정의 → 구조(참여자) → 예시 → 장단점 → 비슷한 패턴과 구분** 순으로 정리. 제목 옆은 최신 기출 위치와 추가 출제 횟수입니다.

#### 생성(Creational) 패턴 — 객체를 어떻게 만들까?

##### 1. Singleton (싱글톤) — 생성·객체 [🔥 23년 2회 11번](../2023년%202회/11.md)
- **정의**: **클래스의 인스턴스가 딱 하나만** 만들어지도록 보장하고, 어디서든 **전역으로 접근**할 수 있게 하는 패턴.
- **구조**: ① `private` 생성자(밖에서 `new` 금지) ② `static` 필드(유일한 인스턴스 보관) ③ `static getInstance()`(없으면 만들고, 있으면 그대로 반환).
- **예시**: 설정 정보, 로그 기록기, **DB 커넥션 풀(DBCP)** 처럼 프로그램 전체가 공유해야 하는 객체. 메모리 낭비를 줄인다.
- **주의**: 멀티스레드에서는 인스턴스가 둘 만들어지지 않게 동기화가 필요하고, 전역 상태라 테스트가 어려우며, '생성 관리 + 업무 로직' 두 책임을 가져 단일 책임 원칙에 어긋난다는 비판이 있다.
- **기출 연결**: Java 싱글톤 문제는 `get()`을 몇 번 호출해도 **같은 객체**라서 필드(count)가 누적되는 것을 묻는다.
- **시험 키워드**: '인스턴스 하나', '전역 접근', 'DB 커넥션 풀'

##### 2. Factory Method (팩토리 메소드) — 생성·클래스 [🔥 21년 3회 16번](../2021년%203회/16.md)
- **정의**: 객체를 만드는 **인터페이스(팩토리 메서드)는 부모 클래스가 정의**하고, **어떤 클래스의 객체를 만들지는 자식(서브) 클래스가 결정**하게 하는 패턴. 별칭 **Virtual Constructor(가상 생성자)**.
- **구조**: Product(제품 인터페이스) ← ConcreteProduct(구체 제품) / Creator(`createProduct()` 선언, 이 제품을 쓰는 업무 로직 포함) ← ConcreteCreator(`createProduct()`를 재정의해 특정 제품 반환).
- **동작**: 부모는 `new 구체클래스()`를 직접 쓰지 않고 `createProduct()`만 호출 → 자식이 재정의한 메서드가 실제 객체를 만들어 준다(= 상속 + 오버라이딩).
- **쓰는 때**: 만들어야 할 객체의 정확한 타입을 미리 알 수 없을 때, 프레임워크 사용자가 내부 컴포넌트를 확장하게 하고 싶을 때.
- **장점** 생성자와 구체 제품의 결합도↓, 새 제품 추가 시 기존 코드 수정 불필요(OCP). **단점** 제품마다 자식 클래스가 늘어난다.
- **구분**: 한 종류의 제품을 서브클래스가 고름(Factory Method) ↔ **관련된 제품군 전체**를 한 번에 생성(Abstract Factory).
- **시험 키워드**: '서브클래스가 생성할 객체를 결정', 'Virtual Constructor', '상위 클래스는 인터페이스만'

##### 3. Abstract Factory (추상 팩토리) — 생성·객체 [🔥 26년 2회 11번](../2026년%202회/11.md) 외 1회
- **정의**: **서로 관련 있는 객체들의 묶음(제품군)** 을 **구체 클래스를 지정하지 않고** 생성하는 인터페이스를 제공하는 패턴. 별칭 **Kit**.
- **구조**: AbstractProduct(제품 종류별 인터페이스: 의자, 소파) / ConcreteProduct(변형별 구현: 모던 의자, 빅토리안 의자) / **AbstractFactory**(제품군의 모든 생성 메서드 선언) / ConcreteFactory(한 변형의 제품만 생성) / Client(추상 팩토리·추상 제품에만 의존).
- **동작**: Client가 `ModernFactory`를 주입받으면 의자·소파·탁자가 **전부 모던 스타일로 짝이 맞게** 만들어진다. 팩토리만 바꾸면 제품군 전체가 한 번에 교체된다.
- **예시**: GUI 툴킷(윈도우용/맥용 버튼·스크롤바 세트), DB 드라이버 세트, 자동차 부품 세트.
- **장점** 제품 간 **호환성 보장**, 구체 클래스와 결합도↓. **단점** 새 제품 '종류'를 추가하려면 모든 팩토리를 고쳐야 하고 클래스 수가 폭증한다.
- **구분**: Factory Method는 '제품 하나', Abstract Factory는 '**제품군(Kit)**', Builder는 '**한 객체를 단계별 조립**'.
- **시험 키워드**: '관련 객체의 제품군', '구체 클래스 지정 없이', 'Kit', '한 번에 교체'

##### 4. Builder (빌더) — 생성·객체 ⬜
- **정의**: **복잡한 객체의 생성 과정과 표현(결과물)을 분리**해서, **같은 생성 과정으로 서로 다른 표현**을 만들 수 있게 하는 패턴.
- **구조**: Builder(조립 단계 인터페이스: 벽 짓기, 문 달기) / ConcreteBuilder(단계 구현 + 결과물 반환) / Product(결과물) / **Director**(단계를 부르는 순서를 정의, 선택 사항) / Client.
- **동작**: Director가 `buildWalls() → buildDoor() → buildRoof()` 순서를 지시하고, 목조 빌더를 쓰면 목조 주택, 석조 빌더를 쓰면 석조 주택이 나온다.
- **쓰는 때**: 생성자 매개변수가 너무 많고 대부분 선택 사항일 때(텔레스코핑 생성자 문제). 햄버거 주문처럼 옵션을 골라 조립.
- **장점** 단계별 생성·일부 단계 지연 가능, 생성 코드를 제품 로직에서 분리. **단점** 클래스가 늘어 복잡도↑.
- **구분**: 'Abstract Factory = 완성된 제품군을 즉시 반환' ↔ 'Builder = 단계별로 조립한 뒤 마지막에 결과를 받음'.
- **시험 키워드**: '생성과 표현 분리', '단계적 조립', '같은 과정 다른 결과', 'Director'

##### 5. Prototype (프로토타입) — 생성·객체 ⬜
- **정의**: **원본 객체를 복제(clone)** 해서 새 객체를 만드는 패턴. 객체 생성 비용이 클 때 유용하다.
- **구조**: Prototype 인터페이스(`clone()` 선언) / ConcretePrototype(자기 자신을 복사해 반환) / Client(`clone()`으로 복사본 획득) / (선택) Prototype Registry(자주 쓰는 원본을 이름으로 보관).
- **동작**: 초기 설정이 복잡한 객체를 한 번 만들어 두고, 필요할 때마다 `new` 대신 `clone()`으로 복사한 뒤 필요한 부분만 수정한다. '도장 찍기'.
- **주의**: **얕은 복사/깊은 복사**를 구분해야 한다(내부에 참조하는 객체도 복사할지). 순환 참조 객체는 복제가 까다롭다.
- **장점** 구체 클래스를 몰라도 복제 가능, 반복되는 초기화 코드 제거. **구분**: 새로 만드는(Factory) ↔ **복사해서 만드는(Prototype)**.
- **시험 키워드**: '복제', '원본을 복사', '생성 비용이 큰 경우', 'clone'

#### 구조(Structural) 패턴 — 객체를 어떻게 엮을까?

##### 6. Adapter (어댑터) — 구조·클래스·객체 [🔥 25년 1회 14번](../2025년%201회/14.md)
- **정의**: **인터페이스가 맞지 않는 클래스끼리 함께 동작**하도록 중간에서 **인터페이스를 변환**해 주는 패턴. 별칭 **Wrapper(래퍼)**.
- **구조**: Client / Target(클라이언트가 기대하는 인터페이스) / **Adaptee**(쓰고 싶지만 인터페이스가 다른 기존 클래스) / **Adapter**(Target을 구현하면서 Adaptee를 감싸 호출을 변환).
- **두 방식**: **객체 어댑터**(Adaptee를 필드로 가짐 = 합성, 일반적) / **클래스 어댑터**(Adaptee를 상속, 다중 상속 가능한 언어).
- **예시**: 110V 플러그를 220V 콘센트에 꽂는 변환기, 구형 라이브러리·타사 API를 새 시스템 인터페이스에 맞추기.
- **장점** 기존 코드를 수정하지 않고 재사용(OCP·SRP). **단점** 클래스·인터페이스가 늘어난다.
- **구분**: Adapter는 '**이미 있는** 두 인터페이스를 맞춤' ↔ Bridge는 '**처음부터** 추상과 구현을 분리 설계'. Facade는 '여럿을 단순 창구로 묶음', Proxy는 '같은 인터페이스로 대리'.
- **시험 키워드**: '호환되지 않는 인터페이스', '인터페이스 변환', 'Wrapper', 'Target/Adaptee'

##### 7. Bridge (브리지) — 구조·객체 [🔥 26년 1회 2번](../2026년%201회/02.md) 외 1회
- **정의**: **기능(추상화) 계층과 구현 계층을 분리**해서 **각각 독립적으로 확장**할 수 있게 하는 패턴. 두 계층을 '다리'로 연결.
- **구조**: **Abstraction**(상위 제어 로직, Implementor 참조를 가짐) / RefinedAbstraction(추상화 확장) / **Implementor**(구현 인터페이스) / ConcreteImplementor(플랫폼별 구현).
- **예시**: 리모컨(기능: 기본 리모컨, 고급 리모컨)과 TV(구현: 삼성, LG)를 분리 → 리모컨 3종 × TV 3종을 클래스 9개가 아니라 3+3개로 해결. 도형(원, 사각형) × 색상(빨강, 파랑).
- **장점** 한 계층을 바꿔도 다른 계층에 영향 없음, 실행 중에 구현 교체 가능, 클래스 폭발 방지. **단점** 결합도가 낮은 단순 구조에는 과설계.
- **기출 키워드**: '**기능의 클래스 계층과 구현의 클래스 계층을 연결**' → Bridge (26-1-2, 22-3-3).
- **시험 키워드**: '기능 계층과 구현 계층 분리·연결', '독립적으로 확장', '다리'

##### 8. Composite (컴포지트) — 구조·객체 ⬜
- **정의**: **개별 객체(Leaf)와 객체들의 집합(Composite)을 똑같이** 다룰 수 있게 **트리 구조**로 묶어 **부분-전체 계층**을 표현하는 패턴.
- **구조**: Component(공통 인터페이스) / **Leaf**(자식 없는 말단 객체, 실제 일을 함) / **Composite**(자식들을 가지며 요청을 자식에게 위임·합산) / Client(Leaf인지 Composite인지 구분하지 않고 사용).
- **예시**: 폴더와 파일(폴더 크기 = 하위 파일 크기 합), 조직도(부서와 사원), 메뉴와 하위 메뉴, GUI 컨테이너와 컴포넌트.
- **장점** 재귀·다형성으로 트리를 단순하게 처리, 새 요소 추가가 쉬움. **단점** 서로 많이 다른 클래스에 공통 인터페이스를 만들기 어렵다.
- **구분**: Decorator도 재귀적 포함 구조지만 목적이 '합산'이 아니라 '**기능 덧붙이기**', 자식이 하나.
- **시험 키워드**: '트리 구조', '부분-전체 계층', '단일 객체와 복합 객체를 동일하게', '폴더와 파일'

##### 9. Decorator (데코레이터) — 구조·객체 ⬜
- **정의**: **원본 객체를 같은 인터페이스의 래퍼로 감싸서, 상속 없이 동적으로 기능을 덧붙이는** 패턴.
- **구조**: Component(공통 인터페이스) / ConcreteComponent(기본 객체) / **Decorator**(Component를 구현하면서 Component 참조를 가짐, 모든 작업을 위임) / ConcreteDecorator(위임 전후에 추가 동작).
- **동작**: `new 크림(new 시럽(new 커피()))` 처럼 겹겹이 감싸면 가격·설명이 층층이 누적된다. 감싸는 순서와 조합을 실행 중에 자유롭게 바꾼다.
- **쓰는 때**: 기능 조합마다 서브클래스를 만들면 클래스가 폭발할 때, 상속이 불가능한 클래스(final)를 확장할 때.
- **장점** 상속보다 유연, 책임을 작은 클래스로 분리. **단점** 래퍼가 많아지면 중간 래퍼 제거·순서 의존 처리가 어렵다. (Java I/O `BufferedReader(new FileReader())`)
- **시험 키워드**: '동적으로 기능 추가', '객체를 감싼다', '상속 대신 합성', '커피에 시럽·크림'

##### 10. Facade (퍼사드) — 구조·객체 ⬜
- **정의**: **복잡한 서브시스템 앞에 단순한 하나의 통합 인터페이스(창구)** 를 제공해 사용을 쉽게 하는 패턴. 내부 구조는 숨긴다.
- **구조**: Facade(어떤 서브시스템 객체를 어떤 순서로 부를지 앎) / 서브시스템 클래스들(Facade의 존재를 모름, 서로 협력) / Client(Facade만 호출).
- **예시**: 호텔 프런트(청소·룸서비스·예약을 한 곳에서), 컴퓨터 `start()` 한 번에 CPU·메모리·디스크 초기화, 주문 처리 API 하나가 재고·결제·배송을 호출.
- **장점** 클라이언트와 서브시스템 결합도↓, 라이브러리 교체 시 Facade만 수정. **단점** 기능이 몰리면 모든 걸 아는 거대 객체(God Object)가 된다.
- **구분**: Facade는 '**여러 객체를 단순화**하는 새 인터페이스', Adapter는 '**기존 인터페이스를 다른 것으로 변환**'. 모두 Wrapper처럼 보이지만 목적이 다르다.
- **시험 키워드**: '통합 인터페이스', '복잡한 서브시스템을 단순하게', '창구', 'Wrapper'

##### 11. Flyweight (플라이웨이트) — 구조·객체 ⬜
- **정의**: **많은 유사 객체가 공통 상태를 공유**하게 해서 **메모리 사용을 줄이는** 패턴.
- **핵심 아이디어**: 상태를 둘로 나눈다. **내재적(intrinsic) 상태** = 모든 객체에 똑같은 불변 값(나무 종류의 질감·색) → **공유**. **외재적(extrinsic) 상태** = 객체마다 다른 값(나무의 좌표) → 사용할 때 **인자로 전달**.
- **구조**: Flyweight(공유되는 객체) / **FlyweightFactory**(이미 만든 Flyweight를 풀에 보관, 요청이 오면 재사용하고 없을 때만 생성) / Context(외재적 상태 + Flyweight 참조) / Client.
- **예시**: 문서 편집기의 글자 모양(폰트 글리프), 게임의 수천 그루 나무·총알, 문자열 풀(String Pool).
- **장점** 메모리 대폭 절약. **단점** 상태 분리 때문에 코드가 복잡해지고, 외재 상태를 매번 계산·전달하면 CPU 비용이 늘 수 있다.
- **시험 키워드**: '객체 공유', '메모리 절약', '공통(내재) 상태', 'Factory 풀'

##### 12. Proxy (프록시) — 구조·객체 [🔥 25년 2회 7번](../2025년%202회/07.md) 외 1회
- **정의**: **다른 객체에 대한 접근을 제어하거나 부가 기능을 주기 위해 대리(대리자) 객체**를 두는 패턴. **실제 객체와 같은 인터페이스**를 따른다.
- **구조**: Subject/Service Interface(공통 인터페이스) / RealSubject(진짜 객체) / **Proxy**(RealSubject 참조를 갖고 요청 전후에 제어 로직 수행 후 전달) / Client(프록시인지 진짜인지 모름).
- **종류**: **가상 프록시**(무거운 객체를 필요할 때까지 생성 미룸=지연 초기화) / **보호 프록시**(권한 확인 후 접근 허용) / **원격 프록시**(네트워크 너머 객체를 로컬 객체처럼, RMI) / **캐싱 프록시**(결과 저장 후 재사용) / 로깅 프록시.
- **장점** 클라이언트 수정 없이 접근 제어·지연 로딩 추가(OCP). **단점** 클래스 증가, 한 단계 거치므로 응답이 느려질 수 있다.
- **구분**: Proxy는 **같은 인터페이스**로 '접근을 통제', Decorator는 같은 인터페이스로 '기능을 추가', Adapter는 '**다른** 인터페이스로 변환'.
- **시험 키워드**: '대리 객체', '접근 제어', '실제 객체 대신', '지연 생성', '네트워크·대용량 객체'

#### 행위(Behavioral) 패턴 — 객체끼리 어떻게 협력할까?

##### 13. Chain of Responsibility (책임 연쇄) — 행위·객체 ⬜
- **정의**: **요청을 처리할 수 있는 객체들을 사슬(체인)로 연결**하고, 각 객체가 **직접 처리하거나 다음 객체로 넘기는** 패턴. 요청자와 처리자를 분리.
- **구조**: Handler(`handle()`과 `next` 참조) / ConcreteHandler(처리 가능하면 처리, 아니면 `next.handle()`) / Client(체인을 구성하고 첫 핸들러에 요청).
- **예시**: 결재 라인(팀장 → 부장 → 이사), 서블릿 필터/인터셉터 체인(인증 → 로깅 → 압축), 예외 처리 catch 순서, 고객센터 1차→2차 상담.
- **장점** 처리 순서 변경·핸들러 추가가 자유로움. **단점** 끝까지 아무도 처리하지 않을 수 있다.
- **기출 연결**: 24-3-6, 21-2-13 등 '행위 패턴' 문제에서 **예시로 나열**되는 패턴(Chain of Responsibility, Command, Observer).
- **시험 키워드**: '처리 못 하면 다음 객체로', '책임 연쇄', '고리(Chain)'

##### 14. Command (커맨드) — 행위·객체 ⬜
- **정의**: **요청(명령)을 객체로 캡슐화**해서 **저장·전달·재실행·취소·로그 기록**을 할 수 있게 하는 패턴. **호출하는 쪽과 실행하는 쪽을 분리**.
- **구조**: Invoker(명령을 보관하고 `execute()`만 호출, 리모컨 버튼) / **Command**(`execute()`, 선택적으로 `undo()`) / ConcreteCommand(Receiver와 인자를 필드로 가짐, 실제 일은 Receiver에게 위임) / Receiver(진짜 일을 하는 객체, 전등) / Client(조립).
- **예시**: 리모컨 버튼과 가전제품, 텍스트 편집기의 실행 취소(Undo)/다시 실행(Redo), 작업 큐·스케줄러, 매크로 기능.
- **장점** 새 명령 추가가 쉽고 undo/redo·지연 실행 구현이 쉬움. **단점** 클래스가 늘어난다.
- **구분**: Command는 '**무엇을 할지(요청)** 를 객체화', Strategy는 '**어떻게 할지(알고리즘)** 를 교체'. Memento는 상태를 저장, Command는 동작을 저장.
- **시험 키워드**: '요청을 객체로 캡슐화', '취소(undo)', '호출과 실행 분리', '로그', '리모컨 버튼'

##### 15. Interpreter (인터프리터) — 행위·클래스 ⬜
- **정의**: **언어(문법)의 규칙을 클래스로 표현**하고, 그 문법으로 작성된 문장을 **해석**하는 패턴.
- **구조**: AbstractExpression(`interpret(context)` 선언) / **TerminalExpression**(더 쪼개지지 않는 종단 기호: 숫자, 변수) / **NonterminalExpression**(다른 표현식들의 조합: 덧셈, 곱셈, 선택) / Context(해석에 필요한 정보, 변수 값 등). 한 문장의 **구문 트리는 Composite 구조**다.
- **예시**: 사칙연산 계산기(`a + b * c`), **SQL 파서**, 정규 표현식, 통신 프로토콜 해석, 간단한 스크립트 언어.
- **특징**: 문법이 단순할 때 적합. 문법 규칙이 많아지면 클래스가 폭증해 유지보수가 어렵다.
- **주의**: '아키텍처 패턴'에도 Interpreter가 있지만 GoF 행위 패턴과는 다른 맥락.
- **시험 키워드**: '문법을 정의·해석', '언어', 'SQL·통신 프로토콜 개발', '수식 계산기'

##### 16. Iterator (이터레이터) — 행위·객체 [🔥 24년 2회 10번](../2024년%202회/10.md)
- **정의**: **컬렉션의 내부 구조를 노출하지 않고** 요소를 **순차적으로 접근**하게 해 주는 패턴. 순회 로직을 컬렉션에서 분리한다.
- **구조**: Iterator(`hasNext()`, `next()`) / ConcreteIterator(현재 위치를 관리하며 실제 순회) / Aggregate/Collection(`createIterator()` 선언) / ConcreteCollection(자신의 Iterator 반환) / Client.
- **예시**: Java `Iterator`, `for-each`, `ArrayList`/`LinkedList`/`HashSet`을 **똑같은 방식**으로 순회, DB의 **CURSOR**.
- **장점** 배열·리스트·트리 등 구조가 달라도 동일한 방법으로 순회, 여러 반복자가 같은 컬렉션을 독립적으로 순회. **단점** 단순한 컬렉션에는 과하다.
- **기출 키워드**: '컬렉션 객체의 **내부 구조를 노출하지 않고 순차적으로 접근**' → Iterator (24-2-10).
- **시험 키워드**: '내부 구조 노출 없이', '순차 접근', '동일한 인터페이스', 'CURSOR'

##### 17. Mediator (미디에이터(중재자)) — 행위·객체 ⬜
- **정의**: 객체들이 서로 직접 통신하지 않고 **중재자 객체를 통해서만** 상호작용하게 해서 **객체 간 결합도를 낮추는** 패턴.
- **구조**: Mediator(알림 인터페이스) / ConcreteMediator(컴포넌트들의 관계를 캡슐화하고 누구를 호출할지 결정) / Colleague/Component(중재자만 알고, 다른 컴포넌트의 존재는 모름).
- **예시**: 채팅방(참가자는 서로 직접 보내지 않고 방을 통해 전달), 항공 관제탑(비행기끼리 직접 교신하지 않음), GUI 대화상자(체크박스 선택에 따라 입력창 활성화를 대화상자가 조정).
- **장점** N:N 의존을 1:N으로 단순화, 컴포넌트 재사용 쉬움. **단점** 중재자에 로직이 몰려 거대해질 수 있다.
- **구분**: Observer는 '**한 방향 통지**(주체 → 구독자)', Mediator는 '**양방향 조율**을 한 곳에 집중'.
- **시험 키워드**: '중재자', '직접 참조 금지', '상호작용 캡슐화', '결합도 감소'

##### 18. Memento (메멘토) — 행위·객체 ⬜
- **정의**: **캡슐화를 깨지 않고** 객체의 **특정 시점 상태를 저장**해 두었다가 **나중에 그 상태로 복원**하는 패턴.
- **구조**: **Originator**(상태를 가진 원본, 스냅샷을 만들고 복원) / **Memento**(상태의 복사본, 원본만 내용을 볼 수 있음) / **Caretaker**(메멘토를 보관만 하며 내용은 못 봄, 보통 스택).
- **예시**: 실행 취소 Ctrl+Z, 게임 세이브/로드, 트랜잭션 롤백, 편집기의 버전 이력.
- **장점** 상태 이력 관리가 캡슐화를 해치지 않음. **단점** 스냅샷을 자주 만들면 메모리를 많이 쓴다.
- **구분**: Command의 undo는 '동작을 거꾸로 실행', Memento는 '**저장해 둔 상태로 되돌림**'. 둘이 함께 쓰이기도 한다.
- **시험 키워드**: '상태 저장·복원', '이전 상태로 되돌리기', 'Ctrl+Z', '세이브/로드'

##### 19. Observer (옵서버) — 행위·객체 [🔥 26년 1회 2번](../2026년%201회/02.md) 외 2회
- **정의**: **한 객체(Subject)의 상태가 변하면 그 객체에 의존하는 다른 객체들(Observer)에게 자동으로 통지**하는 **일대다(1:N) 의존** 패턴. **발행(Publish)-구독(Subscribe)** 모델.
- **구조**: **Subject(Publisher)**(관찰자 목록, `attach/detach/notify`) / ConcreteSubject(상태 보관, 변경 시 `notify()`) / **Observer(Subscriber)**(`update()` 선언) / ConcreteObserver(통지를 받아 각자 반응).
- **동작**: 구독자 등록 → 주체 상태 변경 → `notify()`가 등록된 모든 관찰자의 `update()` 호출. 주체는 구체 관찰자를 몰라도 되므로 **느슨한 결합**.
- **예시**: 유튜브 구독 알림, GUI 이벤트 리스너(버튼 클릭), MVC에서 Model 변경 → View 갱신, 주식 시세 알림.
- **장점** 주체 수정 없이 관찰자 추가·제거 가능(OCP). **단점** 통지 순서를 보장하기 어렵고, 잘못 쓰면 연쇄 갱신이 일어난다.
- **기출 키워드**: '한 객체의 **상태가 바뀌면 그 객체에 의존하는 다른 객체들에 자동 통지**' → Observer (26-1-2, 22-3-3, 20-2-10).
- **시험 키워드**: '상태 변화 통지', '일대다 의존', '발행-구독', '이벤트'

##### 20. State (스테이트) — 행위·객체 ⬜
- **정의**: **객체의 내부 상태에 따라 행동이 달라지게** 하되, **상태별 행동을 별도 클래스로 캡슐화**해서 상태 변경 시 객체가 클래스를 바꾼 것처럼 동작하게 하는 패턴.
- **구조**: **Context**(현재 State 참조, 요청을 State에 위임, 상태 교체 setter) / State(상태별 메서드 인터페이스) / ConcreteState(각 상태의 행동, 필요하면 다음 상태로 전이를 직접 지시).
- **해결하는 문제**: `if (state == A) ... else if (state == B) ...` 같은 거대한 조건문이 여러 메서드에 흩어지는 것.
- **예시**: 신호등(빨강→초록→노랑), 자판기(동전 없음/있음/품절), 문서 결재 상태(작성중/검토중/승인), TCP 연결 상태.
- **장점** 새 상태 추가가 쉽고 조건문 제거. **단점** 상태가 적거나 거의 안 바뀌면 과설계.
- **구분(자주 출제될 수 있음)**: **State = 상태 객체들이 서로 알고 스스로 다음 상태로 전이**, **Strategy = 전략 객체들은 서로 모르고 클라이언트가 선택**.
- **시험 키워드**: '상태에 따라 행위 변경', '상태 캡슐화', '신호등'

##### 21. Strategy (스트래티지(전략)) — 행위·객체 ⬜
- **정의**: **같은 목적의 알고리즘들을 각각 클래스로 캡슐화**해서 **실행 중에 서로 교체**할 수 있게 하는 패턴. 클라이언트에 영향 없이 알고리즘을 바꾼다.
- **구조**: **Context**(Strategy 참조 보유, 작업을 위임, 전략 교체 setter) / **Strategy**(알고리즘 공통 인터페이스) / ConcreteStrategy(개별 알고리즘) / Client(어떤 전략을 쓸지 선택).
- **예시**: 내비게이션의 경로 탐색(자동차/도보/대중교통), 정렬 알고리즘 교체(버블/퀵), 결제 수단(카드/계좌/포인트), 게임 캐릭터의 무기 교체. Java `Comparator`.
- **장점** 알고리즘 교체·추가 쉬움, 조건문(if-else) 제거, 상속 대신 합성. **단점** 클라이언트가 전략 차이를 알아야 하고 클래스 수 증가.
- **구분**: Strategy는 '**어떻게(알고리즘)**' 교체, Command는 '**무엇을(요청)**' 객체화, Template Method는 '**상속**으로 일부 단계만 교체'(Strategy는 합성).
- **시험 키워드**: '알고리즘 캡슐화', '상호 교환 가능', '실행 중 교체', '무기 교체'

##### 22. Template Method (템플릿 메소드) — 행위·클래스 ⬜
- **정의**: **알고리즘의 골격(순서)은 상위(추상) 클래스가 정의**하고, **세부 단계는 하위 클래스가 구현**하게 하는 패턴. 전체 구조는 바꾸지 못한다.
- **구조**: **AbstractClass**(템플릿 메서드 = 단계들을 정해진 순서로 호출, 보통 `final` / 추상 단계 / 기본 구현이 있는 선택 단계 / **훅(Hook)** = 비어 있는 확장 지점) / ConcreteClass(추상 단계 구현).
- **예시**: 라면 끓이기(물 끓이기 → 면·스프 넣기 → 익히기 중 '재료 넣기'만 제품별로 다름), 데이터 처리 `열기 → 읽기 → 처리 → 닫기`, 프레임워크의 라이프사이클 콜백.
- **장점** 공통 코드를 부모에 모아 중복 제거, 변하는 부분만 자식이 구현. **단점** 상속 기반이라 유연성이 낮고 단계가 많아지면 유지보수가 어렵다.
- **구분**: Template Method는 **상속(정적)**, Strategy는 **합성(동적 교체)**. 'GoF **클래스** 범위' 패턴 4개(Factory Method, Adapter, Interpreter, Template Method)로 외워 둔다.
- **시험 키워드**: '골격은 상위, 세부는 하위', '공통 로직 상위 배치', '라면 끓이기', '훅'

##### 23. Visitor (비지터) — 행위·객체 [🔥 23년 2회 11번](../2023년%202회/11.md)
- **정의**: **데이터 구조(요소 클래스)와 그 위에서 수행할 처리(연산)를 분리**해서, **요소 클래스를 수정하지 않고 새로운 연산을 추가**하는 패턴.
- **구조**: Visitor(요소 종류마다 `visit(요소)` 선언) / ConcreteVisitor(연산 구현: 세금 계산, XML 내보내기) / **Element**(`accept(visitor)` 선언) / ConcreteElement(`accept`에서 `visitor.visit(this)` 호출) / Client(요소들을 순회하며 `accept`).
- **더블 디스패치**: ① 클라이언트가 `element.accept(v)` 호출 → ② 요소가 `v.visit(this)` 호출 — 두 번의 호출로 '요소 타입 × 방문자 타입'에 맞는 코드가 실행된다.
- **예시**: 세무사가 집·회사·가게를 방문해 각각 세금 계산, 컴파일러의 구문 트리 탐색(코드 생성/최적화 방문자), 쇼핑 카트 항목별 할인 계산.
- **장점** 새 연산 추가가 쉽다(OCP). **단점** 요소 클래스를 새로 추가하면 **모든 Visitor를 수정**해야 하고, 요소의 비공개 멤버 접근이 어렵다.
- **구분**: '새 **연산** 추가가 잦으면 Visitor, 새 **요소** 추가가 잦으면 부적합'.
- **시험 키워드**: '구조는 두고 연산만 추가', '방문(accept/visit)', '기능 분리', '기존 코드 불변'

### 헷갈리는 패턴 비교 (시험에서 짝지어 나오는 것들)
| 비교 | 핵심 차이 |
|---|---|
| **Factory Method / Abstract Factory / Builder** | 서브클래스가 **제품 하나**를 고름 / **제품군(Kit)** 을 한 번에 / **한 객체를 단계별로 조립**(생성과 표현 분리) |
| **Singleton / Prototype** | 인스턴스를 **하나만** 유지 / 원본을 **복제**해 여러 개 생성 |
| **Adapter / Facade / Proxy / Decorator** | 인터페이스 **변환** / 여러 객체를 **단순 창구**로 / 같은 인터페이스로 **접근 제어** / 같은 인터페이스로 **기능 추가** |
| **Bridge / Adapter** | 처음부터 기능·구현 계층을 **분리 설계** / 이미 존재하는 것들을 **사후에 맞춤** |
| **Composite / Decorator** | 트리로 **부분-전체를 동일 취급** / 한 객체를 **감싸 기능 추가** |
| **Strategy / State** | 전략 객체는 서로 모르고 **클라이언트가 선택** / 상태 객체는 서로 알고 **스스로 전이** |
| **Strategy / Template Method** | **합성**(실행 중 알고리즘 통째 교체) / **상속**(골격 고정, 단계만 재정의) |
| **Command / Memento** | **동작(요청)** 을 객체로 저장 / **상태**를 저장해 복원 |
| **Observer / Mediator** | 주체 → 구독자 **일방 통지(1:N)** / 여러 객체의 **양방향 조율을 한곳에 집중** |
| **Iterator / Visitor** | 컬렉션을 **순차 접근** / 구조는 두고 **연산을 추가** |

### 암기 팁 — 분류별 개수와 이름

## SOLID 원칙 (1회)

### 2022년 2회 06번

[해설 보기](../2022년%202회/06.md)

다음은 SOLID 원칙에 관한 내용이다. 괄호안에 알맞는 단어를 보기에서 고르시오.  
(실제 기출문제에서는 답의 보기가 주어집니다.(오답 중, SRP, LSP 등..))

( ) 은/는 클라이언트가 자신이 이용하지 않는 메서드에 의존하지 않아야 한다는 원칙이다.

( ) 은/는 큰 덩어리의 인터페이스들을 구체적이고 작은 단위들로 분리시킴으로써 클라이언트들이 꼭 필요한 메서드들만 이용할 수 있게 한다.

예를 들어 하나의 복합기에 프린터와 복사기, 팩스 메서드가 있는데 이 세가지 메서드는 같은 파일에 존재하므로 프린터 로직만 바뀌어도 복사기와 팩스도 재컴파일을 해야한다.

그러므로 ( ) 을/를 적용하여 로직이 바뀌어도 다른 메서드는 영향을 받지 않도록 해야한다.

<details><summary>정답 보기</summary>

**정답:** ISP (Interface Segregation Principle, 인터페이스 분리 원칙)

</details>
